# oxi v0.1.0 — Beta

The first beta release of **oxi**, a self-hosted webmail client with a React/Next.js interface and a Rust/Axum backend. oxi connects to an existing IMAP/SMTP service; it does not provide a mail server or host mailboxes.

## Highlights

- **Everyday mail:** read, compose, reply, forward, rich-text/plain-text composition, drafts, attachments, message threads, bulk actions, folders, and tags.
- **Search and live updates:** local SQLite/Tantivy search with sender, recipient, folder, date, and attachment filters; WebSocket updates backed by IMAP IDLE and periodic reconciliation.
- **Contacts and calendar:** address-book groups, autocomplete, vCard import/export, calendar event management, and ICS import/preview.
- **Multiple accounts:** add and switch between accounts in the browser, including per-account server settings; manage sender identities.
- **Personal preferences:** light/dark/system themes, display density, animation settings, keyboard shortcuts, and a command palette.
- **Self-hosting:** one server serves the static frontend and API, with Docker and Nix/NixOS deployment support, including matching frontend/backend subpath builds.

## Getting started

You need an existing IMAP/SMTP account and network access from oxi to your mail servers. Configure `IMAP_HOST` and `SMTP_HOST` for the normal deployment flow, then sign in with your email credentials. The login form also supports server overrides.

For Docker deployments, use the version-pinned image reference:

```bash
docker run -d \
  --name oxi \
  -p 3001:3001 \
  -e IMAP_HOST=mail.example.com \
  -e SMTP_HOST=mail.example.com \
  -v oxi-data:/data \
  ghcr.io/c0h1b4/oxi:v0.1.0
```

The example exposes `http://localhost:3001` and uses the development environment default. **For production, set `ENVIRONMENT=production` and put oxi behind HTTPS**, serving the frontend and API from the same origin. Production session cookies require a secure connection. Configure `TRUSTED_PROXIES` to your actual reverse-proxy IPs/CIDRs when forwarding client IPs for login rate limiting.

Defaults are HTTP port `3001`, IMAP port `993`, SMTP port `587`, and a 24-hour sliding session timeout (`SESSION_TIMEOUT_HOURS`). Keep `/data` persistent and backed up: it contains per-user databases, search indexes, and application data, not just disposable mail caches. See the README and `.env.example` for configuration; source builds use Bun/Node.js and Rust (edition 2024). The frontend static export must be built alongside the server. Nix deployment details are in [`nix/README.md`](https://github.com/c0h1b4/oxi/blob/v0.1.0/nix/README.md).

## Beta cautions and current limitations

- **This is a prerelease.** Test with your own mail server before relying on it for daily use. Keep backups and report reproducible problems with the server type and relevant logs, excluding credentials and private mail.
- Sessions and account credentials are held in server memory. Restarting the server requires signing in again, including when “Keep me logged in” was selected.
- Search covers locally cached/indexed messages, not an immediate full-server search. Background body indexing is opt-in and gradual; mail that has not been fetched/indexed may not appear in body searches.
- Contacts and calendar events are stored locally by oxi; CardDAV/CalDAV synchronization is not implemented. Back up these data before removing the data volume.
- IMAP currently supports implicit TLS or plain TCP, **not IMAP STARTTLS**. Use implicit TLS (normally port `993`) for secure IMAP access. SMTP supports STARTTLS on port `587` and implicit TLS on other TLS-enabled ports (normally `465`).
- Sieve/server-side mail-filter management is not included.
- A subpath deployment requires a frontend built with `NEXT_PUBLIC_BASE_PATH` matching the server's `BASE_PATH`; changing the runtime prefix alone does not rebuild frontend assets. Unrelated cross-site frontend/API hosts are not supported by the documented cookie setup.

## Distribution and upgrades

Docker image: `ghcr.io/c0h1b4/oxi:v0.1.0` (also tagged `0.1.0`). GitHub provides
source archives; standalone binaries are not attached to this release.

Back up your persistent `/data` volume before upgrading and pin the image version
in your deployment. The `latest` Docker tag tracks `main`, not a stable release.
Breaking changes may occur throughout the 0.x beta series.
